# Task 10001 — resumable per-wallet rescan

Status: **deferred, and its default outcome is "drop it".** Do not start before
[[Task 307]] lands. Round 2 of review established that the original one-column
sketch could not deliver what this task promised, so the task now opens with the
decision it has to make rather than a design it cannot support.

## The Decision This Task Must Make First

**A height alone cannot resume a rescan.** Verified: `Rescan` takes a non-empty
`[]RescanTarget`, and `RescanTarget` is `{Scope waddrmgr.KeyScope; AccountID
uint32}` (`wallet/syncer.go`). After a restart a bare `rescan_height` does not
reveal which accounts were targeted, what start was requested, which tip the
scan was walking toward, or whether the job was cancelled or completed. The
original `ALTER TABLE ... ADD COLUMN rescan_height` sketch was therefore a
bandage wearing the word "durable".

So there are exactly two honest options, and this task picks one before writing
any DDL:

**Option A — drop this task.** If restart-from-scratch is acceptable for a
rescan, nothing durable is needed: a rescan is rare, bounded, and idempotent
over immutable global blocks, so re-walking it after a crash costs time and
nothing else. This is the **default**, and it is what "root fixes, not bandages"
implies when the only justification for new schema is convenience.

**Option B — persist a real rescan job.** If resumability is genuinely required,
it needs a job relation, not a column:

```sql
-- One row per rescan job. PostgreSQL: BIGINT GENERATED BY DEFAULT AS IDENTITY.
-- SQLite: INTEGER PRIMARY KEY (rowid alias, auto-assigned). Every other DDL
-- block in this plan carries the per-dialect note; this one must too.
CREATE TABLE wallet_rescan_jobs (
    id BIGINT PRIMARY KEY,             -- see per-dialect note above
    wallet_id BIGINT NOT NULL REFERENCES wallets (id) ON DELETE RESTRICT,

    -- Closed set, following the valid_status pattern (000007:83-85): an open
    -- INTEGER would let any value in.
    state INTEGER NOT NULL CHECK (state IN (0, 1, 2, 3, 4)),
                                       -- 0 running, 1 waiting, 2 stale,
                                       -- 3 completed, 4 cancelled
    requested_start INTEGER NOT NULL CHECK (requested_start >= 0),
    next_height INTEGER NOT NULL CHECK (next_height >= 0),
    target_tip INTEGER NOT NULL CHECK (target_tip >= 0),
    target_revision BIGINT NOT NULL CHECK (target_revision >= 0),

    -- Ownership claim: bumped on every takeover, checked by every progress
    -- write. See "Exclusive ownership" below.
    claim_generation BIGINT NOT NULL DEFAULT 0
        CHECK (claim_generation >= 0),
    updated_at TIMESTAMP NOT NULL
);

-- At most one active job per wallet. Terminal rows are excluded so history can
-- be retained without blocking the next job.
CREATE UNIQUE INDEX uidx_rescan_jobs_active
    ON wallet_rescan_jobs (wallet_id)
    WHERE state IN (0, 1, 2);

-- One row per target of that job.
--
-- Two corrections over an earlier draft, both of which made the table reject or
-- mis-resolve valid requests:
--
-- 1. account_id was NOT NULL with an FK to accounts. But RescanTarget permits
--    waddrmgr.ImportedAddrAccount -- the keyless raw-import bucket, which its
--    own doc says "has no account row" (wallet/syncer.go). Every raw-import
--    target would have failed the FK. So target_kind discriminates, and
--    account identity is nullable.
-- 2. The job_id and (wallet_id, account_id) FKs were independent, so a job
--    owned by wallet A could carry wallet B's id and account and both FKs
--    would pass. The FKs are now composite through the parent, and the
--    resolved scope_id is persisted and enforced, so a target cannot resume a
--    different scope/account pair than the one admitted.
--
-- Neither FK references blocks, so rule 1 is untouched.
CREATE TABLE wallet_rescan_job_targets (
    job_id BIGINT NOT NULL,
    wallet_id BIGINT NOT NULL,

    -- 0 = ordinary account, 1 = raw-import bucket.
    target_kind INTEGER NOT NULL CHECK (target_kind IN (0, 1)),

    -- NULL exactly when target_kind = 1 (the raw-import bucket).
    scope_id BIGINT,
    account_id BIGINT,

    CONSTRAINT check_target_identity CHECK (
        (target_kind = 0 AND scope_id IS NOT NULL AND account_id IS NOT NULL)
        OR (target_kind = 1 AND scope_id IS NULL AND account_id IS NULL)
    ),

    -- Tenancy through the parent: the job's wallet must be this row's wallet.
    FOREIGN KEY (job_id, wallet_id)
        REFERENCES wallet_rescan_jobs (id, wallet_id) ON DELETE CASCADE,

    -- Scope and tenancy through the account, so a persisted target cannot
    -- resolve to a different scope than the admitted request.
    FOREIGN KEY (account_id, wallet_id, scope_id)
        REFERENCES accounts (id, wallet_id, scope_id) ON DELETE RESTRICT
);

-- The target set must actually be a set. Without these a job can store the
-- same account twice, or several raw-import rows, and restart reconstruction
-- would depend on in-memory dedup. Identical in both dialects.
CREATE UNIQUE INDEX uidx_rescan_targets_account
    ON wallet_rescan_job_targets (job_id, scope_id, account_id)
    WHERE target_kind = 0;

CREATE UNIQUE INDEX uidx_rescan_targets_raw_import
    ON wallet_rescan_job_targets (job_id)
    WHERE target_kind = 1;
```

Test duplicate ordinary-account insertion and duplicate raw-import insertion.

Only **one** parent needs new uniqueness: `wallet_rescan_jobs (id, wallet_id)`.
The accounts side already has exactly the required index —
`uidx_accounts_id_wallet_scope` on `(id, wallet_id, scope_id)`
(`pg/migrations/000005_accounts.up.sql:84`, `sqlite/…:86`). An earlier draft
here claimed it lacked `scope_id` and needed adding; it does not.
Tests: cross-wallet target rejected, wrong-scope target rejected, and a
**raw-import target that survives a restart** — the case the earlier FK would
have made impossible.

**Terminal-row policy, decided:** completed and cancelled jobs are **retained**
for audit and excluded from the active-uniqueness index. "Clear or complete" was
two policies wearing one phrase; this is one.

Note what Option B is not: it is not a second chain cursor. It records *which
accounting work was asked for and how far it got*, and it holds the tip and
revision the job was walking toward so a job invalidated by a reorg can be
detected rather than silently resumed against different history.

**Decide A or B, in writing, before any migration is drafted.** Do not
half-implement B.

## The Rules, If Option B Is Chosen

Each exists because breaking it re-creates machinery [[Task 307]] deleted.

1. **No `ON DELETE RESTRICT` to `blocks`.** A job row that pins a block
   reintroduces, per wallet, exactly the RESTRICT web that forced DB-wide
   rollback coordination and produced `ResetChain`, `chainResetCoordinator` and
   `WriteGate`. Store bare heights; no foreign key to `blocks` at all.
2. **The bookmark advances in the same transaction as the accounting it
   describes.** This is the rule the first draft omitted, and the one that
   silently corrupts history if broken: a crash between advancing `next_height`
   and committing the corresponding `ApplyScanBatch` changes permanently skips
   that range, and the reverse order replays it and depends on every accounting
   write being idempotent. So `next_height` moves in the **same Store
   transaction** that commits the transaction/account/horizon changes for that
   range. Starting, advancing, completing and cancelling a job are each one
   atomic transition. **A bookmark must never be ahead of committed
   accounting.**
3. **Clamped inside the rollback transaction — as ordered statements, not one
   statement.** After Task 307 the shared cursor lives in `chain_state` and the
   job rows live elsewhere, so a single statement cannot touch both and SQLite
   has no portable way to fake it. The invariant is **transaction scope, not
   statement count**: inside 307's rollback transaction, clamp every job's
   `next_height`, then update `chain_state` and its revision, then delete the
   block rows. Note also that the clamp expression is not portable —
   PostgreSQL `LEAST(a, b)`, SQLite two-argument `MIN(a, b)` — so the statement
   text differs per dialect even though the behaviour must not.
4. **Never consulted to answer "is this wallet synced?"** That question has one
   answer for the whole database, read from the shared cursor. A job row says
   only how far a rescan walk has progressed.

## Semantics: `next_height`, Not "Progress"

Name and define the cursor as **the next unprocessed height**, never "the last
one done" — that ambiguity is where off-by-one bugs live, especially at genesis
and immediately after a rollback.

- initialize `next_height` to the requested start;
- advance it to one past the last **atomically committed** block;
- on rollback, rebase it with

  ```text
  next_height = max(requested_start, min(next_height, B))
  ```

  where `B` is the rollback **boundary** the API takes (blocks `>= B` are
  removed, so the retained tip is `B-1` — see [[Task 307]]'s boundary section).
  The `max(requested_start, …)` term is not decoration: clamping to the
  boundary alone would rescan blocks the caller never asked for. A job that
  requested start 120, rolled back to boundary 101, must not resume at 101 and
  re-walk 101-119;
- move to terminal state on completion rather than leaving a live cursor.

**When the boundary falls below `requested_start`, the job has no processable
range.** It must transition to `waiting` — not stay `running` and resume outside
its requested range — until the canonical chain reaches its start again.

**Something must then wake it.** A `waiting` job that nobody revisits stays
active forever and holds the partial unique index against the next request. Give
that transition an owner: either [[Task 307]]'s global chain owner observes the
tip reaching `requested_start`, or an explicit resume operation does. Either way
it goes through the same generation-checked `replan` transaction that refreshes
`target_tip`/`target_revision`. Test that a waiting job wakes **exactly once**
after the chain advances far enough.

Crash tests at batch boundaries and at height 0 are mandatory, not optional.

## Reorg Invalidation Needs A Recovery Path, Not Just Detection

Storing `target_revision` detects that a job's history changed, but detection
alone **strands the job permanently**: rollback clamps `next_height` while
leaving the old target tip and revision in place, so every subsequent resume
re-detects the same mismatch and never progresses.

One transactional policy, decided:

1. **Rollback marks *every* active job `stale`** in the same transaction that
   rebases them — not only the ones whose `next_height` exceeded the boundary. A
   job sitting below the boundary is never rebased, but its `target_revision` is
   invalidated all the same, so scoping this to "affected" jobs would strand it
   at the detection step with no replan. Every active job goes `stale`; it is
   one state write and it removes a whole class of stuck rows.
2. **After global sync settles, one `replan` transition** records the new
   `target_tip` and `target_revision`, applies the rebase formula, and returns
   the job to `running` — or to `waiting` if the new tip is below
   `requested_start`. **`replan` owns the rebase.** The rollback transaction
   clamps `next_height` so no row is ever left pointing past the retained tip,
   and `replan` re-applies the same formula against the refreshed tip; the
   operation is idempotent, but `replan` is the transition responsible for the
   final value.
3. Nothing else may resume a `stale` job.

Test multiple successive reorgs, same-height replacement (the case the revision
fence exists for), and a reorg that lands below `requested_start`.

## Exclusive Ownership Is Required, Or This Is Worse Than Option A

`state = running` is **not** an ownership claim. As first drafted, two processes
could resume the same durable job concurrently — and [[Task 307]] explicitly
tests two independently opened stores — so two workers could apply overlapping
accounting batches and race `next_height`. That would make the durable job
*less* safe than restarting from scratch, which is itself an argument for
Option A.

If Option B is chosen it must have:

- the partial unique index above, so at most one active job per wallet;
- a **claim generation** acquired by database CAS, not by reading `state`;
- the expected generation asserted on **every** batch and progress update, so a
  stale worker's write fails instead of interleaving;
- a stable `ErrRescanInProgress` for a second request;
- takeover and stale-worker tests **across two processes**, not two goroutines.

**A generation says how a takeover happens; it does not say when one is
allowed.** Unrestricted claims let two live workers steal the job back and forth
forever; forbidding claims strands a job whose owner crashed. So state the
admissibility rule too — either an **owner plus expiry lease** (a claim is
legitimate once the lease has expired) or an **explicit administrative
takeover** that atomically bumps the generation. Either way, a worker that hits
its first stale-write error **stops permanently** rather than re-claiming. Test
live-owner rejection, crashed-owner takeover, and the absence of a reclaim
loop.

## Caller Cancellation Must Be Defined

A `cancelled` state without a stated boundary is ambiguous: does RPC context
cancellation cancel the durable job, or merely stop that caller waiting while
the Manager continues it? Those give opposite restart behaviour.

Decided contract, mirroring [[Task 10002]]'s acceptance boundary: **cancellation
before durable admission creates nothing; after admission the job continues and
its result stays queryable**, and only an explicit `CancelRescan` winning a
generation-checked transition cancels it. Never infer durable cancellation from
a disconnected RPC waiter.

## Explicitly Out Of Scope: Wallet Onboarding

An earlier draft suggested reusing this mechanism to catch up a newly added
wallet. **It must not, and the two cases differ in exactly the way that
matters.** An ordinary supplemental rescan is optional work, so global sync may
stay true while it runs. Onboarding a wallet whose accounting is *incomplete* is
required work, so under the all-or-none rule the one global status must be
**false** until catch-up finishes — otherwise the wallet reports synced while
missing history.

If onboarding is wanted later, model it as a distinct **required-accounting job
owned by Task 307's global sync state**, not as an optional `Rescan` bookmark.
This keeps 307 small and keeps its "a wallet mid-rescan is still reported
synced" assertion true instead of self-contradictory.

## Verification (Option B Only)

- an interrupted rescan resumes from `next_height` rather than restarting;
- **crash between accounting and bookmark**: injected failure at a batch
  boundary leaves the bookmark no further ahead than committed accounting, in
  both crash orders;
- **a rollback rebases an active job** to `max(requested_start, min(next, B))`
  and the rescan resumes without rescanning deleted blocks **and without
  scanning below `requested_start`** — the second assertion fails if the
  `max(requested_start, …)` term is dropped;
- **a rollback below `requested_start`** moves the job to `waiting`, not
  `running`;
- **reorg recovery, not just detection**: a stale job is replanned once and then
  progresses; test successive reorgs, same-height replacement, and a reorg below
  the requested start;
- **exclusive ownership across two processes**: a second request gets
  `ErrRescanInProgress`, a stale worker's progress write fails its generation
  check, a live owner's job cannot be stolen, a crashed owner's job can be taken
  over, and no reclaim loop occurs;
- **a `waiting` job wakes exactly once** after the chain advances to
  `requested_start`, through the generation-checked `replan`;
- **raw-import target survives a restart** — the case the earlier non-null
  `account_id` FK made impossible;
- **cross-wallet and wrong-scope targets are rejected** by the composite FKs, on
  both backends;
- **cancellation boundary**: a disconnected caller does not cancel an admitted
  job; only `CancelRescan` does;
- **a job never prevents a block delete** — a rollback succeeds with job rows
  pointing above the target;
- **a job invalidated by a reorg is detected** via `target_revision` rather
  than resumed against different history;
- "is this wallet synced?" answers from the shared cursor alone: a wallet
  mid-rescan is still reported synced, and one with no job is not reported
  unsynced;
- two wallets rescanning from different heights do not affect each other's job
  or the shared cursor;
- height-0 and batch-boundary crash cases;
- both backends behave identically.
